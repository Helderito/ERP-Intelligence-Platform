# ADR-0005

# Company/Tenant Model — Shared-Schema CompanyId (revisits ADR-0003)

**Status:** Accepted

**Date:** 2026-09-12

**Decision Makers:**

- Helder Gonçalves

---

# 1. Context

[ADR-0003](ADR-0003.md) deferred multi-tenancy beyond the MVP: no tenant or company identifier exists in any aggregate, and it explicitly stated that "when multi-company support is scheduled, a new ADR shall define the chosen tenancy strategy before any implementation begins." This is that ADR.

The commercial pivot to an Angolan fiscal ERP ([ADR-0004](ADR-0004.md)) changes the premise on which ADR-0003 rested. Fiscal identity in Angola is intrinsically **per company/taxpayer**: NIF, establishments, document series and legal numbering, software/taxpayer keys, SAF-T (AO) submissions and AGT electronic-invoice submissions are all scoped to a single taxpayer. A commercially viable product must also be able to serve **more than one client company** without a separate deployment per client.

Therefore the concern is no longer speculative (the YAGNI argument in ADR-0003) — it is a concrete, near-term requirement that must be settled **before** fiscal and transactional tables are created, to avoid an expensive retrofit of `CompanyId` across them.

---

# 2. Problem Statement

Decide the tenancy strategy and whether a company/tenant identifier is introduced now, before the fiscal and transactional modules are built.

---

# 3. Considered Options

## Option 1 — Continue deferring (status quo of ADR-0003)

Disadvantages: fiscal identity is per taxpayer; deferring forces either a single-company-only product (not commercially viable) or a painful `CompanyId` retrofit across fiscal/transactional tables later. Rejected.

## Option 2 — Shared schema + `CompanyId` + row-level filtering (chosen)

One database and schema; every fiscally/operationally relevant aggregate carries a `CompanyId`; all queries are filtered by the current company, enforced in the application now and by database row-level security later.

Advantages: simplest viable multi-tenant model; low operational overhead; no per-tenant provisioning; easy cross-company administration; introduces the identifier once, before the costly tables exist.

Disadvantages: relies on disciplined, centrally-enforced filtering (a missed filter leaks data across companies); noisy-neighbour and per-tenant scaling handled later.

## Option 3 — Schema-per-tenant / Option 4 — Database-per-tenant

Advantages: stronger isolation.

Disadvantages: significant provisioning, migration and operational complexity; premature for the current stage and cost profile. Can be revisited if a client demands physical isolation.

---

# 4. Decision

Adopt **Option 2**. Introduce a **`Company` aggregate** and a **`CompanyId`** on every fiscally- and operationally-relevant aggregate **from now**, using a **shared schema with row-level filtering by the current company**.

- The initial deployment may serve a single company, but the model is **multi-company-ready by construction**.
- A **current-company context** is resolved per request (from the authenticated user's company membership) and applied as a mandatory filter on all reads and writes of company-scoped data.
- Filtering is enforced in the application layer now (e.g. a global EF Core query filter on `CompanyId`), with PostgreSQL **row-level security** added as defence-in-depth later.
- Existing Master Data aggregates (`Customer`, `Supplier`, `Product`, `Warehouse`, managed reference data) gain `CompanyId` via migration; **globally shared reference data** that is not company-specific (e.g. `Country`, `Currency`, `PaymentTerm` seeded catalogues) remains global and is explicitly exempt.
- Bootstrap seeds a **default `Company`**, and existing rows are backfilled to it.
- This decision **supersedes the deferral in ADR-0003**; ADR-0003 is marked as revisited.

---

# 5. Rationale

Angolan fiscal compliance makes company identity inherent, not speculative — the condition ADR-0003 set for revisiting itself is met. Shared-schema with `CompanyId` is the least-complex model that is genuinely multi-company, and introducing the identifier before the fiscal/transactional tables exist avoids the migration cost ADR-0003 accepted as its main downside. Stronger physical isolation (schema/DB-per-tenant) remains a future option if a client requires it, without invalidating this model.

---

# 6. Consequences

### Positive

- Fiscal isolation per taxpayer is possible from day one (series, numbering, keys, SAF-T, submissions scoped by `CompanyId`).
- The product can serve multiple client companies from one deployment.
- The `CompanyId` is introduced before the costly tables, avoiding a large retrofit.

### Negative

- Every company-scoped query must be filtered correctly; a missed filter is a cross-company data leak — mitigated by a global query filter and later row-level security.
- Adds `CompanyId` and the current-company context to the model and to existing Master Data (a migration and a review of every repository/query).
- Per-tenant scaling and physical isolation are deferred, accepted as a documented trade-off.

---

# 7. Implementation Guidelines

- Model `Company` as the tenant root; `CompanyTaxProfile`/`Establishment` (ADR-0004) hang off it.
- Add a global `CompanyId` query filter; make the current-company context explicit and required for company-scoped repositories.
- Keep global reference catalogues (`Country`, `Currency`, `PaymentTerm`) tenant-agnostic.
- Backfill existing rows to a seeded default company in the migration.
- Add tests asserting cross-company isolation (a company cannot read another's data).

---

# 8. Impact

- [ADR-0003](ADR-0003.md) — revisited/superseded in part.
- [ADR-0004](ADR-0004.md) — provides the per-company fiscal isolation this enables.
- Data Model, Domain Model, Entity Relationship Diagram (`Company` + `CompanyId`).
- Software Architecture Document (§16 Scalability / multi-company).
- All future modules (Inventory, Sales, Purchasing, Finance) are company-scoped from the start.
